**Biggest gaps, in order of risk to the Week 12 demo:**

1. **Week 7 #4, tentative holds expire: not built.** There is only a front-end countdown that never receives data. No expiry column, no release job, no notification, and the back end treats `tentative` as APPROVED. The only spec that mentions it scopes it out. It is mandatory. SCRUM-97 and SCRUM-108 are still To Do.
2. **Draft event requests: save, resume and submit exist; delete does not.** An organiser can save an incomplete request, reopen it, save again and submit it. There is no way to delete a draft (SCRUM-56), nothing checks that the status filter of SCRUM-55 exists, and copying a past request into a new draft is not built. *Save built 2026-10-31 (SCRUM-53, PR #144, Mig/70); resume, re-save and submit built on the SCRUM-54 branch the same day (PR #147, Mig/71 and 72, not yet merged).*
3. **Registrations never become Confirmed.** Every registration is saved Pending (`waitlisted`), and only Confirmed ones count toward capacity, so the capacity cap can never trigger. *Built 2026-10-30 (SCRUM-169): Confirmed up to capacity, Pending beyond it, and the organiser confirms or declines.*
4. **Status management has no transition rules, by decision.** Confirmed, Completed and Cancelled are reached through a free dropdown that accepts any status; the customer said progression is flexible, so guarded transitions are not being built ([scope-decisions.md](docs/scope-decisions.md)). *Cancel now releases the event's venue bookings and equipment and closes its change requests (SCRUM-174, Mig/60 to 63).*
5. **Safety Officer "Reject" and the automatic start: done** (SCRUM-171, Mig/66). Reject returns the event to Planning (W9 r11, r22, r64), and the last arrangement approved moves a Planning event into the queue (W9 r63).
5a. **Two built behaviours contradict the Week 9 answers.** A Confirmed event whose venue becomes unavailable must revert to Planning (W9 r44, r51), but the code leaves the event untouched. The Lead must see and assign across all coordinators (W9 r16, r37), but the code limits the Lead to their own supervised coordinators.
6. **Notifications are in-app only** (no email or SMS). The missing producers were added by SCRUM-172 (Mig/65), except a notice when a venue block is lifted, which needs a way to lift one first.
7. **Row-level security is mostly in place; two gaps remain.** A Lead reads only unassigned events and their own coordinators' events, not every event as the customer says (W9 r37). The reference data and `activity_log` stay open to every signed-in user, on purpose ([ADR 0003](docs/architecture/adr/0003-row-level-security-as-authorisation.md)). A third gap, any coordinator adding a coordinator-history row for any event, is closed by SCRUM-183 (Mig/77), checked on its branch; its PR is open.
8. **Process and documentation gaps:** coverage below the rubric's 100% target (reasons in `docs/testing/coverage.md`, with 39 files still needing tests; no threshold on purpose, SCRUM-173), `context.puml`, `container.puml` and the README out of date, `component-venue-service.puml` still lists the calendar as Planned, and no instructor-access note.

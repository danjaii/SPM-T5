**Biggest gaps, in order of risk to the Week 12 demo:**

1. **Week 7 #4, tentative holds expire: not built.** There is only a front-end countdown that never receives data. No expiry column, no release job, no notification, and the back end treats `tentative` as APPROVED. The only spec that mentions it scopes it out. It is mandatory. SCRUM-97 and SCRUM-108 are still To Do.
2. **No draft event requests on `main`.** A request can only be created already submitted. PRs #144 (save) and #147 (resume) are open and unreviewed.
3. **Registrations never become Confirmed.** Every registration is saved Pending (`waitlisted`), and only Confirmed ones count toward capacity, so the capacity cap can never trigger. SCRUM-169 and SCRUM-170 (In Progress) cover it.
4. **Status management has no transition rules, and cancel releases nothing.** Confirmed, Completed and Cancelled are reached through a free dropdown that accepts any status. Cancelling an event does not free its venue bookings or equipment, which the Week 1 briefing calls out as a problem to fix.
5. **Safety Officer "Reject" is a dead end, and the check does not start by itself.** The decision is recorded and nothing else happens; the customer says Reject returns the event to Planning (W9 r11, r22, r64). The customer also says the review starts automatically once venue and technical arrangements are confirmed (W9 r63), but an event only reaches the queue after someone sets Awaiting Arrangements by hand. SCRUM-171 (In Progress) covers both.
5a. **Two built behaviours contradict the Week 9 answers.** A Confirmed event whose venue becomes unavailable must revert to Planning (W9 r44, r51), but the code leaves the event untouched. The Lead must see and assign across all coordinators (W9 r16, r37), but the code limits the Lead to their own supervised coordinators.
6. **Notification producers are missing** for event submission, venue approve/reject, important changes, registration updates, confirmation and cancellation. In-app only, no email or SMS. SCRUM-172 (In Progress) covers the producers, not email or SMS.
7. **Row-level security is mostly in place; three gaps remain.** A Lead reads only unassigned events and their own coordinators' events, not every event as the customer says (W9 r37). Any coordinator can add a coordinator-history row for any event (`Mig/14:184`). The reference data and `activity_log` stay open to every signed-in user, on purpose ([ADR 0003](docs/architecture/adr/0003-row-level-security-as-authorisation.md)).
8. **Process and documentation gaps:** no coverage threshold on `main` (SCRUM-173 is in progress; 100% is a rubric target), no traceability matrix, `context.puml`, `container.puml` and the README out of date, `component-venue-service.puml` still lists the calendar as Planned, ADR 0003 still marked "Proposed", and no instructor-access note.

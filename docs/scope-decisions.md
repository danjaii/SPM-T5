# Scope decisions

Requirements we considered and chose not to build, or to build only in part, for Release 1. Each row says what the
customer said and where the decision is recorded, so the reasoning can be found from the requirement's own name.

The customer's answers come from the weekly Q&A spreadsheets (Week 2: `G1G2 Week2 Clarification.xlsx`, Week 9:
`G1G2 clarification Answers wk9.xlsx`) and the customer briefing (`Project Brief.pdf`).

| Requirement considered | Decision | Why | Recorded in |
| --- | --- | --- | --- |
| Guarded status transitions: limiting which status an event can move to from its current one | Not built for Release 1. The one rule the customer insists on is already enforced: an event cannot be Confirmed until it is Safety Approved (`events_safety_gate`, migration 37), and it only reaches the safety check once every venue booking and equipment request is approved (`is_ready_for_safety_check()`, same migration). | The customer said in the Week 2 Q&A that transition rules "are open to design assumptions; status progression is generally flexible for now", and that changes of status need "the proper discussion of workflow later when it is needed for implementation". The customer briefing asks only that events "progress through suitable statuses so that users can understand their current stage". The one rule the customer did set, in the Week 9 Q&A: "All required venue and technical arrangements must be approved, and safety check completed, before the Coordinator marks the event as Confirmed." | SCRUM-174 (Out of scope), [cancel-event.md](specs/cancel-event.md) |
| Organisers cancelling an event themselves | Not built. Organisers ask their coordinator, who cancels it (SCRUM-174). | The customer said in the Week 2 Q&A that "Organisers can request changes/cancellation at any point in time", and in the Week 9 Q&A that "modifications or withdrawals must be requested through the Coordinator." | SCRUM-174 (Out of scope), [cancel-event.md](specs/cancel-event.md) |
| VIPs without an account: an organiser adding a guest who has never signed up | Not built. A VIP must already have an attendee account, and the organiser adds them by its email (SCRUM-170). | The customer allows adding VIPs by hand past the normal cap, up to venue capacity (Week 4 answer, row 5), and does not mention inviting guests. The team agreed the account rule when planning the story. | SCRUM-170 |
| The venue capacity limit for VIPs on an event with several venues | Narrowed to the smallest approved venue's capacity. | The customer's answer doesn't cover several venues. Using the smallest means everyone Confirmed fits in each venue, in line with each venue being checked on its own; it can be too strict for sessions running in parallel. | SCRUM-170 |
| Editing a layout type's description, and retiring a layout type (`is_active`) | Not built. "Edit" a layout type is built as rename; Venue Staff add, rename and delete layout types (SCRUM-181). | The customer said in the Week 9 Q&A that Venue Staff define layout types and can add, edit and delete them. The story's acceptance criteria name add, rename and delete only, and nobody asked for a description or a retire step; `GET /events/request-options` also offers inactive layouts, so retiring would need that fixed first. | [layout-type-maintenance.md](specs/layout-type-maintenance.md) (Out of scope, open question 4) |
| A separate switch for a coordinator to pause registration while an event is re-planned | Narrowed. Registration is closed automatically while the event is not Confirmed, and the coordinator can adjust the capacity and the window, which includes closing it early. There is no "paused" flag. | The customer said in the Week 9 Q&A that, when an event goes back to Planning, registration "may be paused or adjusted by the coordinator". An event in Planning is already not listed and cannot be registered for, so a flag would add a second way to say the same thing; the part that was missing, adjusting capacity and the window, is built (SCRUM-185/AC4). | [registration-settings-while-replanning.md](specs/registration-settings-while-replanning.md) (Implementation decisions) |
| Event names on the venue calendar's blocks (the Figma 09 and 09a mock-ups label each booking, e.g. "Annual Tech Summit"), and in 09a's week view who set a block, its notes, how many bookings it affects, when a hold expires and a View request button | Not built. A block names its status ("Confirmed", "Tentatively Held") and its times; Requested and Hold are one status, Tentatively Held, as the API sends them (SCRUM-130). | The calendar is read by Event Coordinators and Technical Support Staff as well as Venue Staff, and the venue calendar spec decided it never returns the event, coordinator or requester of a booking (SCRUM-84 spec, AC2 S6, after 36-S5 and 105-S6); `venue_calendar_entries()` (migration 58) returns none of these, nor a booking id to link to. Showing them would undo that decision, which is a change for the team rather than a restyle. | SCRUM-130 PR, [SCRUM-84 spec](specs/SCRUM-84-venue-availability-calendar.md) |
| Any start and end date on the venue calendar | Narrowed to Day, Week and Month with a previous/next stepper and Today, as in Figma 09 (SCRUM-130). Venue-service still accepts any range up to 62 days. | The mock-up shows only the three views and the stepper; a month covers the longest range a user picked in practice, and a fixed view cannot ask for an invalid range. | SCRUM-130 PR |
| "+ New booking" on the venue calendar (Figma 09) for Venue Staff | Narrowed. New booking is shown to Event Coordinators only: it lists their events that can still take a venue request and opens that event's Request a venue page (SCRUM-130). Venue Staff and Technical Support Staff do not see it. | Only the event's assigned coordinator can request a venue booking (SCRUM-32); venue-service and the database refuse anyone else. Letting Venue Staff create bookings would change who may book, with new rules in the database, which is a story of its own rather than a restyle. | SCRUM-130 PR |
| A separate home page (dashboard) for the Event Coordinator Lead (SCRUM-162) | Replaced. The Lead's home is the Unassigned requests queue: `/dashboard/event_coordinator_lead` forwards to `/lead/queue`, and the Lead's sidebar has no Home item (SCRUM-188). | The dashboard showed the number of unassigned requests and the coordinators' workloads, which the queue page already shows beside the queue itself (SCRUM-126), so it was one more click before the Lead's real work. The address is kept, not removed, because sign-in, `/`, the access-denied page and "Back to dashboard" send every role to `/dashboard/<role>`. | SCRUM-188 |
